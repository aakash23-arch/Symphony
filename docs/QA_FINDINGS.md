## Executive Summary

The VoiceShield system was subjected to adversarial black-box, white-box, API stress, and end-to-end user journey evaluations covering all 20 required QA dimensions. 

Overall, the foundational engineering rigor is strong:
- Strict Pydantic contracts reject invalid payloads, negative amounts, and unauthorized context overrides (`extra="forbid"`).
- WebSocket audio ingress at `/v1/sessions/{id}/audio` properly enforces handshake protocol boundaries.
- Persistence across SQLite and transaction ledger state transitions (`PENDING` -> `HELD` -> `APPROVED` / `REJECTED`) work reliably.
- Truthful model status reporting on `/health` correctly reflects offline and unavailable states without unhandled crashes.

However, several critical policy, confidence-scoring, and UI/demo discrepancies were uncovered that degrade demonstration fidelity under competitive judging conditions.

## Detailed QA Findings

### BUG-01: Scenario 2 (AI Impersonation) Triggers `STEP_UP` Instead of `HOLD`
* **Classification:** **P1 (Major)**
* **Area:** `voiceshield.decision.policies` / `voiceshield.fusion`
* **Reproduction:**
  1. Start application backend and frontend.
  2. Navigate to `http://localhost:5173/` -> DEMO MODE.
  3. Select **Scenario 2 — AI Voice Impersonation** (CFO impersonation, ₹25,00,000, new beneficiary, secrecy, callback refusal).
  4. Click `Start Scenario Call`.
  5. Observe policy decision and transaction state.
* **Expected:**
  * Risk Band: `HIGH` or `CRITICAL`.
  * Matched Policy: `P-SUSPICIOUS-VOICE-HIGH-VALUE` or `P-CRITICAL-CONTEXT-HOLD`.
  * Policy Action: `HOLD`.
  * Transaction State: Automatically placed on `HELD`.
* **Actual:**
  * Composite Risk Score reaches `1.00` (Critical), but Confidence Score drops to `0.21`.
  * Rule 2 (`P-INSUFFICIENT-CONFIDENCE`) matches prior to high-risk context rules because `confidence < 0.35`.
  * Decision output: `action=STEP_UP`, `matched_policy=P-INSUFFICIENT-CONFIDENCE`.
  * Transaction state remains `PENDING`.
* **Probable Cause:**
  In `voiceshield/risk/policies.py`, Rule 2 evaluates `confidence < 0.35` and unconditionally outputs `STEP_UP` before evaluating critical context triggers (e.g. ₹25L transfer with identity mismatch + untrusted VoIP). When acoustic evidence confidence is degraded, high-risk context signals are subordinated to step-up verification.
* **Proposed Fix:**
  Add a high-priority policy rule `P-CRITICAL-CONTEXT-HOLD` or elevate `P-SUSPICIOUS-VOICE-HIGH-VALUE` above `P-INSUFFICIENT-CONFIDENCE` when context risk is extreme ($R_{context} \ge 0.85$ on high-tier transactions), ensuring hostile calls are put on hold regardless of low acoustic confidence.

### BUG-02: Scenario 1 (Genuine Executive) Triggers `STEP_UP` Instead of `ALLOW`
* **Classification:** **P1 (Major)**
* **Area:** `voiceshield.signal_processing` / `voiceshield.demo`
* **Reproduction:**
  1. In DEMO MODE, select **Scenario 1 — Genuine Executive**.
  2. Click `Start Scenario Call`.
  3. Observe risk decision.
* **Expected:**
  * Risk Band: `LOW`.
  * Matched Policy: `P-ORDINARY-CALL`.
  * Action: `ALLOW`.
* **Actual:**
  * Risk Band: `UNCERTAIN`.
  * Matched Policy: `P-INSUFFICIENT-CONFIDENCE`.
  * Action: `STEP_UP`.
* **Probable Cause:**
  The synthetic audio fixture `clean_speechlike.wav` generated by `make_demo_fixtures.py` consists of frequency-modulated sine sweeps rather than human speech phonemes. The spectral feature extractor computes a low signal-to-noise ratio ($SNR \approx 12\text{ dB}$) and low speech frame probability, resulting in a call quality index $q_{call} = 0.14$. Low $q$ heavily discounts expert belief weights, keeping total confidence $C \approx 0.21 < 0.35$, which forces fail-safe uncertainty.
* **Proposed Fix:**
  1. Replace synthetic sine-wave sweeps with real human speech audio samples (e.g. LibriSpeech or public domain voice recordings) using `scripts/fetch_speech_samples.py`.
  2. Alternatively, calibrate the quality heuristic baseline for demo fixtures so clean test audio evaluates to $q \ge 0.80$.

### BUG-03: Missing Manual Transaction Hold/Release Controls in Demo UI
* **Classification:** **P2 (Moderate)**
* **Area:** `frontend/src/components/` (Transaction Panel)
* **Reproduction:**
  1. Start any demo scenario.
  2. Look for operator intervention controls (e.g. "Place Hold", "Release Funds", "Reject Transaction") in the live transaction card.
* **Expected:**
  * When a call triggers `STEP_UP` or `HOLD`, compliance operators should have visible UI buttons to manually trigger `POST /api/transactions/{id}/hold` and `POST /api/transactions/{id}/release`.
* **Actual:**
  * Transaction status is displayed as a badge (`PENDING`), but interactive Hold/Release action buttons are omitted from the main demo view.
* **Probable Cause:**
  Frontend transaction card is currently rendered in read-only telemetry mode; API endpoints exist on backend (`/api/transactions/{id}/hold`), but are not wired to interactive UI buttons.
* **Proposed Fix:**
  Add an "Operator Actions" section to `TransactionCard.tsx` with "Place Immediate Hold" and "Release (Approve / Reject)" modal triggers linked to the respective backend endpoints.

### BUG-04: E2 Raw-Waveform Cold Warmup Stalls Startup by ~45 Seconds
* **Classification:** **P2 (Moderate)**
* **Area:** `voiceshield.models.bootstrap` / `Wav2Vec2SpoofAdapter`
* **Reproduction:**
  1. Execute `.venv\Scripts\python -m voiceshield all-in-one`.
  2. Measure time until `/health` returns HTTP 200.
* **Expected:**
  * Fast developer startup (<5 seconds) with asynchronous background warmup or lightweight mock weights for dev mode.
* **Actual:**
  * Startup blocks on `register_experts()` synchronous PyTorch weight deserialization for 45-53 seconds before opening HTTP listener.
* **Probable Cause:**
  `register_experts()` runs in the synchronous FastAPI `@app.on_event("startup")` handler, executing heavy weight loads on the main thread before starting the Uvicorn event loop.
* **Proposed Fix:**
  Execute model warmup in a background thread or `asyncio.create_task()` during startup, reporting `status: "warming_up"` on `/health` until complete without blocking the HTTP listener.

### BUG-05: Analysis Backpressure Warning Logged During Fast Replay
* **Classification:** **P3 (Cosmetic)**
* **Area:** `voiceshield.orchestration.analysis`
* **Reproduction:**
  1. Trigger demo scenario with speed multiplier `speed=2.0`.
  2. Inspect backend logs.
* **Expected:**
  * Replay stream buffers frames without dropping frames under standard demo speeds.
* **Actual:**
  * Log emits `{"level": "WARNING", "message": "analysis backpressure; frame dropped", "frame_id": 9, "dropped_total": 1}`.
* **Probable Cause:**
  Analysis worker queue buffer size (`maxsize=10`) is saturated when audio frames are pushed at 2x clock speed faster than single-threaded CPU inference.
* **Proposed Fix:**
  Increase replay buffer queue capacity or adjust frame pump pacing to match inference consumer throughput.

### BUG-06: Starlette & FastAPI Deprecation Warnings
* **Classification:** **P3 (Cosmetic)**
* **Area:** `backend/voiceshield/api/app.py`
* **Reproduction:**
  1. Run `pytest tests/test_demo_scenarios.py`.
* **Expected:**
  * Clean test output with 0 deprecation warnings.
* **Actual:**
  * Emits `DeprecationWarning: on_event is deprecated, use lifespan event handlers instead.` and `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated`.
* **Probable Cause:**
  FastAPI 0.115+ deprecates `@app.on_event("startup")` in favor of `@asynccontextmanager lifespan(app: FastAPI)`.
* **Proposed Fix:**
  Migrate `@app.on_event("startup")` and shutdown handlers in `backend/voiceshield/api/app.py` to modern FastAPI `lifespan` context manager.

1. **Fix Policy Gating (BUG-01)** so high-risk context triggers `HOLD` directly on Scenario 2.

3. **Add Interactive Hold/Release UI Controls (BUG-03)** to showcase manual operator oversight.
